# Sessão 11/09/2026 — no ar

O pedido: o site pronto para mostrar numa reunião no mesmo dia — público se desse, servidor
local se não.

**Está no ar**, no domínio de produção do projeto `biblioteca-de-assets` na Vercel. O servidor
local de produção ficou de reserva em `localhost:3000`, subido antes de qualquer outra coisa.

## Como

- O conector da Vercel desta sessão não enxergava conta nenhuma (`teams: []`). A CLI da Vercel,
  sim: já estava logada na conta do dono.
- A primeira tentativa de criar o projeto foi barrada pelo sistema de permissões — criar
  recurso na conta de alguém é ação externa e persistente. Perguntei, e o dono respondeu
  "quero subir na vercel".
- `vercel api` criou o projeto — time `nihon2`, Next.js, Root Directory `apps/web`, ligado a
  `NihonCodingg/lol-assets` — e disparou o primeiro deploy de produção a partir do `main`
  (`e11fdc5`). O build levou menos de um minuto.
- No Git Bash, `vercel api /v11/projects` falhava com "Invalid arguments": o MSYS converte o
  caminho num caminho do Windows. `MSYS_NO_PATHCONV=1` resolve — o mesmo tropeço do `/indice`
  de sessões anteriores.

## Conferido contra a URL publicada

| | |
|---|---|
| `conferir-publicacao.mjs` | **26 de 26** |
| `conferir:navegador` | **9 de 9**, inclusive o cenário de HTTPS, que só roda no ar |
| Domínio de produção | 200, sem login |
| Endereço com o sufixo do time | 302 para o login da Vercel |

A proteção padrão do time veio como `all_except_custom_domains`: o domínio de produção é
aberto, e os endereços com sufixo e os de cada deploy pedem login. O checklist passou a dizer
isso onde diz o que compartilhar.

## Um 409 que não se confirmou

Ao pedir o domínio sem sufixo, a Vercel respondeu 409, "já atribuído a outro projeto". Minutos
depois o deploy terminou com esse mesmo domínio atribuído a **este** projeto. A mensagem não
correspondia ao que aconteceu; o que vale é o domínio respondendo, e ele responde.
